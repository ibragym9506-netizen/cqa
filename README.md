# CQA — оценка качества диалогов операторов

Прототип Conversation Quality Analytics для Freedom Broker (хакатон CQA). Система оценивает работу оператора
в чатах и звонках по настраиваемому чек-листу. По каждому критерию она показывает ответ, баллы, объяснение и
ссылку на реплику-доказательство. Оценку можно оспорить, а проверяющий подтверждает или меняет её с причиной.

Модель — **Gemini 3.5 Flash Lite** (бесплатный тариф Google AI Studio, внешний API). Поверх неё работают
детерминированные правила кода и голосование нескольких прогонов.

---

## Быстрый запуск

Нужен Python 3.10+ (проверено: 3.12 на Windows, 3.13 на Linux).

```bash
git clone https://github.com/ibragym9506-netizen/cqa.git
cd cqa
python -m venv venv
venv\Scripts\activate            # Windows;  в Linux/macOS: source venv/bin/activate
pip install -r requirements.txt
```

Создайте в папке проекта файл `.env`:

```
GEMINI_API_KEY=ваш_ключ_из_aistudio.google.com
```

Запустите сервер:

```bash
python server.py                 # Windows: py server.py
```

и откройте **http://localhost:8000**.

Без ключа Gemini интерфейс тоже работает: оценка идёт эвристиками, а готовые оценки набора DEV
подставляются из `results/chat_v1/`.

### Необязательные настройки `.env`

| Переменная | Что делает | По умолчанию |
|---|---|---|
| `GEMINI_API_KEY` | ключ или несколько ключей через запятую (у каждого проекта Google своя квота) | — |
| `GEMINI_MODELS` | цепочка моделей: основная, затем запасные | `gemini-3.5-flash-lite,gemini-3.1-flash-lite` |
| `VOTES` | сколько независимых прогонов модели на одну оценку | `3` |
| `HOST` | `0.0.0.0` — открыть сайт с других устройств в той же сети | `127.0.0.1` |
| `PORT` | порт сервера | `8000` |

## Как пользоваться

Интерфейс состоит из трёх разделов.

**Диалоги**
- **Загрузка.** Вставьте ссылку GET организаторов (`…&group_id=…`) и нажмите «Загрузить». Можно поменять
  только `group_id` в соседнем поле. Ещё можно загрузить JSON-файл или вставить текст диалога
  («Клиент: …», «Оператор: …»).
- **Оценка.** Кнопка «Оценить неоценённые» оценивает весь набор и показывает, сколько запросов к модели это займёт.
- **Сводка.** Средний балл, число оценённых диалогов и грубых ошибок. Клик по «грубые ошибки» оставляет
  в списке только такие диалоги.
- **Сдача.** «Сохранить results.json» записывает файл в формате организаторов: `results/dev/results.json`
  для набора DEV, `results/prod/results.json` для контрольного.

**Карточка диалога**
- Слева переписка. У звонков над ней плеер: ▶/⏸, ±10 с, переход к соседней реплике, скорость.
  Реплика, которая сейчас звучит, подсвечивается.
- Справа критерии: ответ, баллы, вес, объяснение, реплики-доказательства. Для пропущенного действия
  показан проверенный участок, для N/A — причина. Вверху итог и баллы по секциям.
- Ссылки «№12» в объяснениях ведут к нужной реплике, а у звонков ещё и перематывают запись.
- «Оспорить» подаёт апелляцию по критерию с комментарием.

**Апелляции.** Проверяющий видит спорную оценку, комментарий, обоснование и фрагмент диалога. Он
подтверждает оценку или меняет её, указывая причину, и система пересчитывает итог. По желанию можно
запросить «второе мнение» модели, это один запрос. В карточке остаются исходная оценка, решение и новый итог.

**Чек-лист.** Можно менять формулировку, вес, тип ответа (Да/Нет, шкала, флаг), доступность N/A и ступени
шкалы, добавлять и удалять критерии. «Сохранить как новый» создаёт новую версию и делает её активной.
Кнопка «Применить к набору» дооценивает только изменённые критерии: оценки неизменённых сохраняются, потому
что привязаны к смыслу критерия.

### Контрольный набор (сценарий проверки)

1. «Диалоги» → вставить ссылку с новым `group_id` → «Загрузить».
2. «Оценить неоценённые» (10 чатов × 3 прогона = 30 запросов).
3. «Сохранить results.json → prod», затем commit и push.
4. Замена критерия: «Чек-лист» → изменить критерий → «Сохранить как новый» → «Применить к набору».

## Как устроена оценка

```
транскрипт ──► факты кода ──► Gemini × 3 прогона ──► голосование ──► правила кода ──► расчёт баллов
                (язык клиента,   (JSON по схеме,      (большинство;     (проверяемые      (веса, N/A,
                 первая реплика   temperature 0)        расхождение →      случаи)           округление)
                 оператора,                             «стоит проверить»)
                 события, паузы)
```

- **Факты кода.** Перед диалогом модель получает то, что код определяет точно: язык клиента, первую и
  последнюю реплику оператора, подтверждение личности, событие завершения, удержание, долгие паузы.
- **Подсказки к критериям.** Это уточнения из чек-листа и ответов организаторов. Например: неотвеченный
  вопрос снижает консультацию, а не ведение диалога; платная услуга — это грубая ошибка и сама по себе
  эмпатию не снижает.
- **Голосование.** Модель оценивает диалог 3 раза независимо, побеждает большинство. Если прогоны
  разошлись, диалог помечается «стоит проверить».
- **Правила кода** исправляют модель там, где ответ проверяется детерминированно:
  - приветствие и имя в первой реплике оператора;
  - завершение: прощание, закрытие чата, обрыв связи;
  - клиент переспросил или поправил оператора → ведение на ступень «переспрашивать»;
  - раскрытие данных счёта до идентификации → грубая ошибка;
  - «Нет» по идентификации без раскрытия данных → N/A;
  - снижение ведения только за неотвеченный вопрос → снимается.

  Каждое срабатывание видно в карточке («Правило кода поправило модель…»).
- **Расчёт баллов** (`scoring.py` и движок в браузере): шкала пересчитывается пропорционально весу, вес
  N/A перераспределяется между применимыми критериями, итог из 100 округляется до двух знаков, грубая
  ошибка отмечается отдельно.
- **Лимиты и отказы.** При упоре в минутный лимит оценщик ждёт и повторяет ту же модель. Когда кончился
  дневной лимит, он переходит на следующий ключ, затем на запасную модель. При перегрузке модели сразу
  переходит к следующей. Неверный ключ пропускается.

**Проверка точности.** Мы вручную проверили 65 диалогов DEV по чек-листу. Вслепую, без доступа к оценкам
модели, часть диалогов разметили участники команды. Спорные случаи перепроверяются скриптом `recheck.py`:
после правил кода 31 из 32 спорных оценок совпадают с ручной проверкой.

**Стоимость.** Используется бесплатный тариф Gemini API, поэтому оценка ничего не стоит. Одна оценка —
это 3 прогона по ~3,5 тыс. входных и ~1,2 тыс. выходных токенов. Лимиты бесплатного тарифа:
15 запросов в минуту и 500 в день на ключ.

### Звонки: привязка реплик к записи

Время в транскрипте звонка не совпадает со временем в записи: запись ставится на паузу во время перевода
на оператора, начинается не с первой реплики, а метка ставится ближе к концу фразы. Поэтому
`tools/audio_sync.py` находит каждую реплику в самой записи:

1. VAD (silero) делит запись на фрагменты речи.
2. Офлайн-модель sherpa-onnx (zipformer, русский) распознаёт их со временем каждого слова.
3. Слова транскрипта выравниваются со словами распознавания.

Для звонков DEV разметка уже встроена в интерфейс. Новые звонки сервер размечает сам в фоне после
загрузки набора (`POST /api/sync`, кеш в `sync_cache/`). Если слова не распознались (другой язык, шум),
время считается по меткам транскрипта с учётом пауз записи и выравнивается по началам речи. Модели
распознавания (27 МБ) лежат в `models/`, интернет для них не нужен.

## Хранение данных

| Что | Где |
|---|---|
| Чек-листы, оценки, апелляции, решения проверяющего | `data/state.json` на сервере, общий для всех пользователей. Правки с разных компьютеров сливаются по отметкам времени, изменения других приходят за ~4 с |
| Готовые оценки пакетного прогона | `results/chat_v1/*.json` (`batch.py`, `recheck.py`, `rescore.py`) |
| Файлы для сдачи | `results/dev/results.json`, `results/prod/results.json` |
| Копия загруженного набора | `data_<group_id>.json` |

Браузер держит локальную копию, поэтому без сервера интерфейс тоже открывается (только эвристики).

## Встраивание в Dynamics 365

Интерфейс — чистые HTML, CSS и JS без сборки, в одном файле `static/index.html`. Все стили и элементы
живут внутри контейнера `.cqa` и не затрагивают остальную страницу. Чтобы встроить его как
HTML web resource, достаточно задать адрес сервера оценки до загрузки скриптов:

```html
<script>window.CQA_API_BASE = "https://cqa.ваш-сервер";</script>
```

Интерфейс общается с движком через единый контракт `request(method, path, body)`. Поэтому хранилище можно
заменить (например, на Dataverse), не трогая экраны.

## API сервера

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | модель, число прогонов, доступность распознавания речи |
| POST | `/api/fetch` | загрузить набор по ссылке организаторов (без CORS) |
| POST | `/api/llm/evaluate` | оценить диалог по критериям |
| POST | `/api/llm/second-opinion` | повторная оценка одного критерия при апелляции |
| GET, PUT | `/api/state` | общее хранилище (чтение и слияние правок) |
| POST | `/api/results` | записать `results/<dev\|prod>/results.json` |
| GET | `/api/precomputed` | готовые оценки пакетного прогона |
| GET | `/api/audio?u=…` | прямая ссылка на файл записи звонка |
| POST | `/api/sync` | привязать реплики звонка к записи |

## Скрипты

| Файл | Назначение |
|---|---|
| `server.py` | сервер: интерфейс, оценка, хранилище, записи звонков |
| `evaluator.py` | оценщик: факты, промпт, Gemini, голосование, правила кода |
| `scoring.py` | расчёт баллов по правилам чек-листа |
| `batch.py` | пакетная оценка набора: `python batch.py data_DEV.json` |
| `rescore.py` | применить текущие правила кода к готовым оценкам без запросов к модели |
| `recheck.py` | перепроверить спорные диалоги и сравнить с ручной проверкой |
| `try_model.py` | пробный прогон другой модели без сохранения |
| `fetch_audio.py` | скачать записи звонков в `audio/` |
| `tools/audio_sync.py` | привязка реплик звонков к записи (`--setup` скачивает модели) |
| `checklist.json` | исходный чек-лист для пакетных скриптов |
| `static/index.html` | интерфейс и движок (чек-листы, баллы, апелляции) |
